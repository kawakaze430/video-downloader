PROJECT IDEA: ONE DOWNLOAD AND MEDIA WORKSPACE
Detailed product proposal, existing-work inventory, limits, and future roadmap
Prepared: 17 November 2026
Working repository: kawakaze430/video-downloader
Status: planning document for owner review; no new implementation authorized

==========================================================================
01. THE CENTRAL IDEA
==========================================================================

Build a trusted desktop application that helps people collect downloadable
files and permitted videos, recover interrupted transfers, choose available
media quality, process their own media, and keep everything organized.

The user should experience one product: a desktop app, a small browser
companion, a local media-processing engine, and later an optional website or
remote companion. Several programming languages can serve that one product.
We do not need to force every component into one language to make it unified.

The long-term ambition is broad coverage: YouTube, Facebook, Instagram, other
social/video sites, direct MP4 links, and permitted streaming formats. The
honest product promise is:

  "Save, manage, and process the media you are allowed to download, with
   clear quality choices, reliable recovery, and privacy by default."

That is stronger than advertising "download absolutely everything" and then
failing silently. Every supported source must have a tested capability record.
When something cannot be downloaded, explain whether the reason is permission,
DRM, a missing adapter, an expired link, a network issue, or an actual defect.

The product's value should come from reliability and the complete workflow:

  Find a permitted source -> choose what exists -> download reliably ->
  verify the result -> process locally if wanted -> organize -> find it later.

AI can improve search, accessibility, organization, and diagnostics. The core
download manager must still work without an AI subscription or cloud account.
The name, branding, pricing, and final license remain owner decisions.

03. REUSE PRIORITIES: WHAT TO TAKE FIRST
==========================================================================

Priority 1: evaluate AB Download Manager plus its matching browser integration.
They are the primary recommendation in the existing research. Build and test
them before deciding that we need a new engine or desktop framework.

Priority 2: connect the original test fixture to that foundation. Prove one
direct-file job, progress, interruption recovery, checksum verification, and
explicit browser-to-desktop handoff. This turns research into product evidence.

Priority 3: add local media processing through a carefully packaged FFmpeg
integration. Validate codecs, output integrity, cancellation, and licensing.

Priority 4: selectively evaluate MediaGrabber ideas/components for the media
features that are actually missing. Avoid shipping two competing job engines,
two independent histories, or two incompatible browser-to-desktop protocols.

Priority 5: use ReClip as a simplicity benchmark for the interface. Design any
public hosted backend separately with authentication, quotas, safe network
access, persistence, cleanup, and an approved operating budget.

Optional later: evaluate yt-dlp for specifically approved source connectors.
An extractor existing in yt-dlp does not establish permission, stability,
browser-store acceptance, or support in our product. It is not installed or
integrated merely because this document mentions it.

Do not automatically combine all five applications or every researched tool.
Keep one job system and clear interfaces; reuse only what passes the gates.

04. WHO THE PRODUCT SERVES
==========================================================================

Everyday users:
  Reliable downloads, clear progress, safe pause/resume, an understandable
  destination folder, and useful explanations when a source stops working.

Creators and editors:
  Back up their own permitted uploads, organize project assets, select audio
  tracks, extract audio, convert local footage, and prepare supported formats.

Students and researchers:
  Save materials that permit offline use, keep source references, import
  captions, and later search or transcribe media they are entitled to process.

Power users and small teams:
  Batch intake, queues, scheduling, duplicate detection, predictable naming,
  automation, and later an authenticated CLI/API or self-hosted workspace.

Accessibility users:
  Keyboard navigation, screen-reader support, readable errors, captions,
  optional transcription, and clear differences between original and generated
  content. Accessibility belongs in the core UI, not only an AI add-on.

First success story:
  A user starts a permitted large-file download from the browser, loses the
  connection, restarts the computer, and completes the file without corruption
  or confusing duplicate jobs. That should work before ambitious AI features.

05. "EVERY TYPE OF VIDEO": DEFINE THE SCOPE CORRECTLY
==========================================================================

A website, a transport protocol, a container, and a codec are different things.

  Website/platform: YouTube, Facebook, Instagram, Vimeo, a creator's website.
  Transport: HTTPS direct file, HLS playlist, MPEG-DASH manifest.
  Container: MP4, MKV, WebM, MOV, M4V, TS, AVI, and others.
  Codec: H.264, HEVC/H.265, VP9, AV1, AAC, Opus, and others.

MP4 is a container, not a website. A video page URL may require an approved
source resolver; it is not necessarily a downloadable MP4 URL. A browser
blob: URL is normally a local object reference, not a durable network link.

Our support model should have four layers:

  1. Direct downloadable files.
  2. Authorized, non-DRM streaming manifests and segments.
  3. Explicitly supported platform connectors and official export routes.
  4. Local conversion/organization of files the user already has.

Platform priorities and limitations:

YouTube:
  Make permitted creator backups, official export/download routes, and
  rights-reviewed integrations an explicit product research track. The
  YouTube API is not a general raw-video download API. An offline subscription
  feature does not automatically authorize exporting ordinary MP4 files.
  Do not promise unrestricted downloading or Chrome Web Store eligibility.
  Publish actual supported workflows after policy and technical validation.

Facebook:
  Explore user-owned media exports and sources that explicitly permit saving.
  Page videos, Reels, live recordings, private groups, and ephemeral stories
  need different capability entries. Visibility or account access alone does
  not mean unrestricted export is permitted or technically available.

Instagram:
  Explore permitted backups of the user's own media and supported exports.
  Reels, feed videos, stories, and live recordings are separate source types.
  A public post is not automatically an authorized downloadable source.
  Do not promise access to expired stories or private content without access.

Other social/video sites:
  TikTok, X, Reddit, Vimeo, Dailymotion, Twitch, and similar sites are later
  candidates, not advertised support merely because they are listed here.
  Add each only with a specific allowed workflow, tests, and a maintainer.

Creator websites, open media, and direct MP4/WebM/MOV links:
  Strong early candidates where download permission and valid access exist.
  Redirects, expiring URLs, missing lengths, and Range behavior still need
  handling. Support ordinary files as well as videos in the core engine.

HLS and MPEG-DASH:
  Support permitted non-DRM test streams in later stages. Correctly join
  segments, choose variants and tracks, and distinguish live from on-demand.
  Encryption/DRM requirements are not interchangeable. Missing access rights
  or protected keys cannot be solved just by supporting the manifest format.

Live streams:
  A future recording feature can save available, permitted content while
  running, with storage/time limits and gap reporting. It cannot recreate
  earlier segments that the source no longer provides. DVR is source-specific.

Local files:
  Accept supported user-owned media for conversion, repair attempts, caption
  workflows, and organization. Damaged files, missing streams, unsupported
  codecs, and hardware limits still affect results.

==========================================================================
06. MEDIA AND QUALITY ROADMAP
==========================================================================

Phase A: download original files without unnecessary conversion.
  Direct HTTPS downloads should preserve the original bytes. Use declared
  checksums when available; a locally computed hash identifies a result but
  alone does not prove it matches the publisher's intended content.

Phase B: inspect and remux compatible media.
  Show container, codecs, resolution, frame rate, duration, audio languages,
  and subtitles where discoverable. Remux MP4/MKV/WebM only where the target
  container supports the existing streams. Remuxing avoids quality loss.

Phase C: transcode when necessary and requested.
  Offer tested device/quality presets and honest CPU/GPU, size, and time
  estimates. H.264/AAC in MP4 may be a compatibility preset; AV1, HEVC, VP9,
  HDR, and unusual profiles need explicit build/device coverage.

Phase D: audio and subtitle tools.
  Original audio extraction when compatible; conversion to selected supported
  formats such as MP3, M4A, Opus, WAV, or FLAC; SRT/VTT import/export; audio-track
  selection; and later optional transcript generation and subtitle translation.

Quality rules:
  - Show only resolutions and tracks actually available to that workflow.
  - Never label upscaled 1080p as original 4K/8K.
  - Never label a lossy source converted to FLAC as restored lossless audio.
  - Do not assume highest resolution means best quality or best compatibility.
  - Explain when audio and video arrive separately and require merging.
  - Display HDR/SDR and conversion changes when detectable.
  - Mark AI enhancement as generated processing, with the original preserved.

"All formats" is a direction, not a fixed promise: actual support depends on
the source, shipped codec build, patents/licensing, OS, hardware, and tests.

==========================================================================
07. THE EXPERIENCE WE WANT USERS TO HAVE
==========================================================================

Home: one input area for a permitted URL, local file, or batch of links.
The browser companion can send an explicit user-selected item to the same job
system. Avoid forced clipboard monitoring or automatic account inspection.

Preview: show the recognized source, available formats/tracks, size estimate,
save folder, and any limitations. Unknown size or quality must say "unknown".
An unsupported source should produce a useful reason, not a fake download.

Choose: original file, best available compatible media, audio only, subtitles,
or an approved conversion preset. Advanced controls remain available without
making the normal flow complicated.

Download: real bytes, speed, ETA when meaningful, retry state, pause/cancel,
and queue position. Separate transfer progress from merging/conversion.
Unknown-length streams must not show invented completion percentages.

Recover: explain whether the source supports resume. If the remote file
changed or the signed URL expired, require safe re-resolution or restart;
do not join unrelated bytes or claim recovery that cannot be verified.

Finish: verify required integrity checks, move completed output atomically
where supported, and offer open folder, play, convert, or organize. Never
silently overwrite an existing file or auto-run downloaded executables.

Library: optional searchable local history, folders, tags, source references,
and duplicate checks. Users can clear history without deleting media, or
delete media with an explicit action. Retention and private mode are clear.

Example future user request:
  "Save these permitted links in a queue, keep original video, select English
   audio where available, and put them in my course folder."

The app can convert that request into a preview. Natural-language AI must not
silently start paid processing, change destinations, or broaden permissions.

08. FIRST RELEASE: SMALL ENOUGH TO PROVE
==========================================================================

Recommended starting pair: Windows desktop plus Chrome, subject to owner
approval and actual build compatibility. Linux cloud checks support development
but do not substitute for Windows installation and browser testing.

P0: the smallest useful beta
  - Reproducible build of the selected desktop foundation.
  - Direct HTTPS downloads and safe redirects.
  - Accurate progress, queueing, concurrency limits, pause/cancel/retry.
  - Resume where supported and safe restart where not supported.
  - Persisted jobs and recovery after app/system interruption.
  - Safe filenames, collision handling, and incomplete-file cleanup.
  - Expected-hash validation for controlled test downloads.
  - Explicit, authenticated browser-to-desktop handoff with duplicate control.
  - A minimal accessible interface, clear errors, and private local storage.
  - Dependency/license inventory and documented installation/uninstallation.

P0 acceptance demonstration
  1. Start one synthetic permitted HTTPS download from the browser.
  2. Show exactly one desktop job and meaningful progress.
  3. Interrupt it; resume safely if the endpoint supports ranges.
  4. Repeat with a Range-disabled endpoint and confirm safe restart.
  5. Restart the app during a recoverable job and finish without corruption.
  6. Verify output SHA-256 against the known fixture value.
  7. Reject unauthorized handoff attempts and unsafe output paths.
  8. Confirm clean install and uninstall on the supported OS, and document
     the update strategy.

Not part of P0: universal platform extraction, cloud accounts, a plugin store,
mobile apps, AI generation, subscriptions, or multi-OS release promises.

09. COMPETITIVE 1.X FEATURES AFTER THE CORE WORKS
==========================================================================

Reliability and control:
  Scheduling, bandwidth limits, measured segmented transfers where useful,
  duplicate handling, job-list import/export, search, categorization, and
  network settings. More connections do not always mean more speed.

Browser convenience:
  Right-click actions, user-triggered permitted media detection, paired
  desktop progress, transparent permissions, and later Edge/Firefox validation.
  Do not run separate engines just because multiple extension sources exist.

Media studio:
  Local probing, tested remux/conversion presets, audio extraction, track and
  subtitle selection, basic trimming, and compatible-file merging. Batch jobs
  should have independent results so one failure does not lose the whole batch.

Platform connectors:
  One approved source/workflow at a time, with a capability page, fixture or
  authorized integration tests, regression monitoring, and a maintenance owner.

Daily usability:
  Keyboard access, readable errors, localization, storage warnings, sleep/power
  handling, optional completion notifications, and an explainable retry policy.

Trustworthy distribution:
  Signed installers and verified updates, release notes, rollback strategy,
  dependency notices, opt-in redacted diagnostics, and a support process.

Website:
  Start with product information, supported-source information, installation
  guides, documentation, and release downloads. A hosted downloader is a
  separate, later operating and security decision, not a prerequisite.

10. ONE PROJECT, MULTIPLE LANGUAGES
==========================================================================

Recommended proposal, not an approved architecture change:

  Kotlin desktop foundation:
    Keep the existing queue, transfer state, persistence, and desktop UI
    where they pass tests. This preserves the largest reusable investment.

  TypeScript browser companion:
    Handle user intent, source discovery, capability presentation, and
    authenticated handoff. Browser code ultimately executes as JavaScript.

  FFmpeg media worker:
    Perform supported media operations through a constrained, versioned
    interface. FFmpeg is external software, not a reason to rewrite the UI.

  Python:
    Preserve the original fixture and use tests/tools where useful. Do not
    add a permanent Flask backend just because ReClip happens to use Flask.

  Shared contract:
    Define a small versioned job/message schema. Adapt existing AB contracts
    where sensible rather than introducing another engine or state database.
    The desktop remains the authority for local jobs and files.

A typical future flow:

  Browser companion -> authenticated native bridge -> desktop job engine
  Desktop UI --------------------------------------> desktop job engine
  Desktop job engine -> local job store -> safe temporary/completed files
  Desktop job engine -> optional isolated media worker -> verified output
  Optional AI module -> approved local files/metadata -> suggestions or index

Prefer native messaging for the first browser bridge after auditing the
existing protocol. A loopback HTTP service, if retained, still needs explicit
authentication, origin controls, validation, and rate/resource limits.

Possible future integrated layout, only after owner approval:

  apps/desktop/       selected desktop application
  apps/extension/     selected browser companion
  apps/website/       optional public information site
  components/media/  media-processing interface and workers
  components/sources/ approved source adapters
  contracts/         shared protocol definitions
  tests/             fixtures and integration checks
  docs/              decisions, capability records, releases

This is an illustration. The current sources/ snapshot layout is not being
restructured again by this document.

==========================================================================
11. SHOULD WE MOVE TO ONE LANGUAGE?
==========================================================================

Option A: retain Kotlin plus TypeScript and small supporting tools.
  Best initial option to evaluate because it preserves existing source work.
  Cost: more than one toolchain and careful cross-process interface testing.
  Benefit: focus effort on integration and actual missing features.

Option B: TypeScript-centered rewrite, for example a web-based desktop shell.
  Could share UI types and some business logic across browser/web/desktop.
  It does not automatically port the Kotlin transfer engine, persistence,
  installers, OS integration, or recovery behavior. Those still need migration
  and tests. Some shells also introduce another native language/toolchain.
  FFmpeg and platform-specific code remain external even in this approach.

Option C: a mostly Kotlin product.
  Preserves the desktop foundation, but browser extensions still need browser
  APIs and JavaScript-compatible output. ReClip and MediaGrabber logic would
  not simply become Kotlin by moving files. Build size and platform behavior
  need evidence before expanding this direction.

Option D: a mostly Python product.
  Convenient for tooling and selected media adapters, but does not remove
  browser JavaScript, desktop packaging, security, or performance work.
  Rewriting a mature desktop engine into Python is not a free simplification.

Decision rule:
  First build and benchmark the existing foundation. Compare integration
  costs, maintenance skills, install size, memory, reliability, and security.
  Rewrite only if there is evidence that maintaining the current foundation
  is materially worse. No migration is approved by this proposal.

12. MAKE SOURCE SUPPORT A MAINTAINED PRODUCT CAPABILITY
==========================================================================

Keep a support record for every advertised source/workflow:

  - Platform, content type, and permitted use case.
  - Access/export method and any supported authentication route.
  - Direct file, stream, or connector and exact adapter version.
  - Available formats, quality, audio, subtitle, playlist, and live limits.
  - Tested OS/browser, date, test result, and maintenance owner.
  - Distribution/store restrictions and known failure explanations.

Use statuses such as:
  Planned; under investigation; available for testing; supported within
  stated limits; temporarily degraded; unsupported; restricted by policy.

Never advertise a large site count by copying another tool's extractor list.
Do not claim "supported" merely because the adapter imports successfully.
One platform may support an authorized creator export but not private stories,
live recording, or general third-party downloads. Show that distinction.

Keep these separate:
  Can the user access it? Does the workflow permit exporting it? Does our
  adapter support it? Did the output actually pass its integrity/media checks?
  A single "I own this" checkbox cannot answer all four questions.

If a platform changes, mark the affected capability degraded, retain useful
error details locally, and ship a reviewed fix. Do not silently attempt more
intrusive access methods or broaden browser permissions.

13. AI FEATURES THAT COULD MAKE THE PRODUCT BETTER
==========================================================================

AI should solve a real user problem. It should not replace deterministic
transfer logic, integrity checks, or permission decisions.

First useful additions, after the reliable core:

  Smart assistance:
    Explain errors in plain language using redacted diagnostic facts. Suggest
    a compatible preset, identify likely duplicates, and explain size/quality
    tradeoffs. Keep the underlying error code and non-AI help available.

  Transcription and captions:
    Produce a searchable transcript for supported owned/licensed media. Show
    language, timestamps, model/version, and processing location. Let users
    correct errors. Label generated captions separately from original captions.

  Personal media search:
    Search local titles, tags, captions, and optionally semantic indexes.
    Show the matching file and time range, so users can inspect the result.
    Delete related indexes when requested; do not make a public media index.

  Translation and chapter suggestions:
    Offer editable subtitle translations, topic markers, and candidate chapters.
    Preserve the original text. Names, accents, specialist language, and mixed
    languages can produce errors; accuracy needs measurement and correction.

  Safe natural-language automation:
    Convert a request into a visible plan: destination, filters, conversion,
    schedule, and estimated resource use. The user approves material actions.
    A model cannot expand source permissions or silently delete/share files.

Later research candidates:

  - Scene-based organization and selected highlight suggestions.
  - Local duplicate/similar-media analysis with reversible decisions.
  - Speech cleanup, denoising, stabilization, and optional enhancement.
  - Assisted accessibility descriptions for user-selected media.
  - An assistant that helps diagnose a connector regression in development.

Conditions for shipping an AI feature:
  A measurable benefit, a test set, known failure cases, a disable switch,
  clear CPU/GPU/RAM needs, predictable cost, and explicit processing location.
  Local inference is preferred where practical; cloud processing is opt-in.
  Do not upload private videos or transcripts by default or claim a model is
  private just because the rest of the application runs locally.

Downloaded titles, transcripts, pages, and metadata are untrusted data.
An AI assistant must not treat text inside them as instructions to execute
commands, leak credentials, alter settings, or contact outside services.

AI-generated enhancement is a new version, not recovery of an authentic
missing original. Preserve the source and label generated changes clearly.

14. WHAT CANNOT BE PROMISED, WHAT IS DEFERRED, WHAT WE EXCLUDE
==========================================================================

These are different categories. A feature that we have not built is not
automatically impossible. A technically conceivable feature is not
automatically permitted, suitable for release, or worth maintaining.

A. Promises that are not credible, now or after one or two years

  "Every video from every website, forever."
    Sites change, remove media, restrict exports, expire links, and require
    different clients or permissions. A maintained, scoped catalogue is viable;
    a permanent universal guarantee is not.

  "Any private/deleted/expired video can be recovered."
    Without a lawful accessible source or an existing authorized copy, the
    app may have nothing to retrieve. AI cannot reliably recreate the original.

  "Every video is available in original 4K/8K."
    Only the source's available variants can be retrieved. Upscaling synthesizes
    detail and must not be sold as a higher-resolution original download.

  "Resume always works."
    It depends on server support, source consistency, valid authorization,
    and durable state. A safe full restart is sometimes the correct behavior.

  "Downloads are always 10x faster."
    The bottleneck may be the source, connection, server limits, disk, or CPU.
    Segmentation helps only under suitable conditions and needs fair benchmarks.

  "AI subtitles, translations, or summaries are always correct."
    Models make errors. Editing, references, uncertainty, and fallbacks matter.

  "Every codec plays on every device."
    Hardware and software support differ. Conversion can improve compatibility
    but takes resources and may lose quality or metadata.

  "Unlimited free cloud downloads and AI processing."
    Bandwidth, storage, compute, support, and abuse handling have real costs.
    Local-first operation reduces costs; it does not eliminate them.

B. Capabilities outside the intended product scope

  - DRM removal or access-control, paywall, authentication, or regional-control
    circumvention. These are not future roadmap commitments.
  - Secretly collecting account cookies, passwords, private messages, or tokens.
  - Promising that owning/viewing content automatically satisfies platform
    export rules, distribution restrictions, or all copyright obligations.
  - Misrepresenting browser-store approval or legal compliance as guaranteed.
  - Automatic reposting, impersonation, or removal of provenance/rights notices.

C. Technically plausible but deferred until evidence and approval

  - More source connectors and supported playlist/channel workflows.
  - Permitted live recording and scheduled acquisition while available.
  - macOS/Linux releases and additional browsers after the first target works.
  - Mobile companions; full mobile engines require separate OS-specific work.
  - Local semantic search, transcription, translation, and enhancement.
  - Private remote control, team workspaces, and optional self-hosting.
  - A curated plugin ecosystem with enforceable permissions and isolation.

Revisit deferred features at milestones. Do not reopen fundamental physical,
privacy, or permission constraints just because AI tools become more capable.

15. A ROADMAP FOR NOW, ONE YEAR, TWO YEARS, AND BEYOND
==========================================================================

Baseline: November 2026. These are planning horizons, not delivery promises.
Progress depends on owner choices, staffing, budget, source compatibility,
release requirements, and actual acceptance results. Move dates when a gate
fails; do not label an unfinished feature complete to meet a date.

Stage 0: next approved work, roughly the first 0-3 months

  Objective:
    Preserve prior research, choose the first foundation, and make one reliable
    desktop download workflow reproducible.

  Work:
    Confirm the product's initial OS/browser and license/distribution direction.
    Inventory source versions, dependencies, notices, and third-party assets.
    Reproduce the desktop build with the required toolchain and resolve setup
    problems. Recheck historic extension type/security findings against the
    supplied snapshots. Test the transfer engine with controlled HTTP/HTTPS.

  Exit evidence:
    A repeatable build and a narrow tested vertical slice: direct download,
    progress, safe resume/restart, persisted state, and matching fixture hashes.
    Record failures rather than bypassing verification.

Stage 1: approximately months 3-6

  Objective:
    Make desktop and browser behave like one product for the first supported
    platform pair.

  Work:
    Authenticated pairing, explicit handoff, job deduplication, progress,
    permission minimization, installer work, and crash/interruption testing.
    Begin local FFmpeg processing only after the core contract is stable.

  Exit evidence:
    A user installs the app and extension on a clean test machine, creates
    exactly one job, resumes safely where possible, and cannot trigger the
    helper from an unauthorized webpage. Core installer and data-safety tests
    pass. Any beta limitations are visible.

Stage 2: by around November 2027, the one-year horizon

  Target:
    A dependable beta or 1.x candidate for the chosen OS/browser, subject to
    the earlier gates rather than the calendar alone.

  Candidate features:
    Strong queue/history/search, scheduling, tested local conversions,
    permitted non-DRM HLS/DASH, selected supported source workflows, subtitle
    tools, accessible UI, and documented update/release procedures.
    Add signed distribution, redacted diagnostics, and regression monitoring.
    Trial basic opt-in AI assistance only if it produces a measured benefit.

  Exit evidence:
    Supported-source matrix, complete core test results, clean-machine release
    checks, notices/SBOM, recoverable update behavior, and beta feedback that
    confirms reliability. Do not require AI or a large site count to ship.

Stage 3: by around November 2028, the two-year horizon

  Target:
    Sustainable expansion rather than an uncontrolled feature list.

  Candidates:
    Additional OS/browser targets where maintainable; more approved connectors;
    a personal media library with opt-in transcription and semantic search;
    a stable CLI or authenticated automation API; and a limited private
    self-hosted dashboard if demand justifies its cost and security work.

  Exit evidence:
    Maintainers for each connector/platform, measured AI quality and latency,
    bounded cloud costs if any, privacy deletion/export tests, compatibility
    tests, and a working release/support process. Disable stale capabilities
    instead of pretending their support is permanent.

Stage 4: 2029 onward, three years and beyond

  Research candidates, not commitments:
    A mobile companion, trusted-device sync, team workflows, a curated plugin
    SDK, better local multimodal search, advanced media enhancement, and
    constrained personal automation across approved devices and sources.

  Entry gate for each:
    Users want it; someone can maintain it; it has a viable privacy/security
    design; licensing and platform rules allow it; resource/cost targets are
    acceptable; and a small prototype proves the claimed benefit.

At every horizon the durable advantage is user trust, recovery, usable
interfaces, and fast maintenance. "AI era" is a reason to improve execution
and usefulness, not to assume technical or platform limits will disappear.

16. WHO WILL BUILD AND MAINTAIN THESE FEATURES?
==========================================================================

The project owner remains the decision maker. The roles below are
responsibilities, not a requirement to hire a separate person for every line.
A small team can combine them; one person plus AI will need a smaller scope.

Owner/product lead:
  Sets priorities, approves scope/foundation choices, selects brand/license,
  decides budgets and distribution, and accepts or rejects milestone results.

Desktop engineer:
  Owns transfer reliability, persisted jobs, filesystem safety, OS behavior,
  resource use, and the main application's integration with the chosen engine.

Browser engineer:
  Owns extension UX, host permissions, packaging, pairing/native messaging,
  and compatibility with explicitly supported browsers.

Media/connector engineer:
  Owns tested FFmpeg profiles, format/track handling, approved platform
  adapters, error categories, and capability regression monitoring.
  These can become separate roles if support volume grows.

QA/security/release owner:
  Owns fixture coverage, negative/security tests, clean-machine installation,
  dependency and binary provenance, update integrity, and release evidence.
  External review may be useful before public or commercial distribution.

AI engineer, when justified:
  Owns model evaluation, inference options, language quality, resource/cost
  measurements, prompt/data boundaries, consent, and reliable non-AI fallbacks.

Design, accessibility, support, and policy/license review:
  Own a readable product, usable errors, supported-user feedback, appropriate
  notices, and source/distribution decisions. Assign named owners as work starts.

AI coding tools:
  Can assist implementation, tests, diagnosis, documentation, migration analysis,
  and release preparation. They do not replace accountable maintainers, actual
  device/browser tests, owner approvals, or professional legal review.

Who else might pursue similar ideas in future?
  Existing download-manager teams, browser-tool developers, media editors,
  open-source communities, and personal-AI-assistant vendors may add overlapping
  features. Their exact future roadmaps are unknown. We should compete on a
  dependable workflow and privacy, not on claiming no one else can build it.

Do not defer all difficult work to a hypothetical future AI. Assign an owner,
a small experiment, a cost ceiling, and a pass/fail gate, or keep it deferred.

17. PRIVACY, TRUST, AND SOURCE LICENSING
==========================================================================

Local by default:
  Direct downloads and ordinary local conversion should not require a cloud
  account. Store sensitive data in appropriate OS facilities; redact private
  URLs and tokens in diagnostics. Let users control history and indexing.

Explicit access:
  Prefer official authentication/export routes when available. Do not silently
  read cookies or send browser credentials to a remote service. A broad host
  permission or localhost address does not make a bridge safe by itself.

Media and worker isolation:
  Treat URLs, filenames, manifests, and media metadata as untrusted. Use safe
  process arguments, bounded workers, predictable cancellation, and maintained
  parsers. Test disk-full, path collision, malformed input, and crash behavior.

If hosted services are approved later:
  Authenticate, restrict outbound destinations/protocols, validate redirects
  and resolved addresses, limit resource use, isolate jobs, and delete retained
  media on a clear schedule. ReClip's interface can inspire simplicity without
  treating its backend as production-ready for arbitrary public requests.

Source licenses:
  AB desktop and AB browser integration supply Apache-2.0 licenses.
  MediaGrabber and ReClip supply MIT licenses.
  The Downloader blueprint supplies no root LICENSE; do not invent one.
  Root licenses are a starting point. Review all transitive dependencies,
  assets, trademark use, notices, and distributed binaries before shipping.
  FFmpeg licensing depends on the exact build and enabled components.

Existing GPL/AGPL research candidates are not automatic product dependencies.
Using one requires a conscious compatible licensing/distribution decision.
This document neither selects a product license nor determines legal approval.

18. HOW TO MEASURE WHETHER THE PROJECT IS GOOD
==========================================================================

Reliability:
  Completion rate on a defined permitted test corpus; restart/recovery success;
  output integrity; and frequency of lost, duplicated, or stuck jobs.

Performance:
  Throughput compared fairly with a single-connection baseline, memory/CPU,
  startup time, disk overhead, and conversion time on named hardware. Measure
  real bottlenecks rather than advertising an arbitrary acceleration factor.

Media correctness:
  Correct selected tracks, duration, audio/video synchronization, playable
  output, subtitle timing, and honest quality/container/codec reporting.

Connector health:
  Last validated date, supported workflows, regression rate, and time to
  diagnose/repair breakage. A source with no maintainer should not be promised.

Usability:
  Time and steps to complete the first download; understandable errors;
  keyboard/screen-reader task completion; and user-reported recovery success.

AI quality:
  Transcription error on representative languages, search relevance,
  translation correction burden, assistance accuracy, latency, and resource
  cost. A language-specific result does not prove universal language quality.

Release and privacy:
  Install/update/uninstall success; clean-machine reproducibility; no secret
  values in diagnostics; verified index/media deletion; and signed artifacts.

Initial numerical targets should be set after a baseline, with a fixed test
set and hardware/network conditions. Do not invent present success rates.
Fixture tests are necessary infrastructure, not the complete product test suite.

19. COST, OPERATING MODEL, AND POSSIBLE BUSINESS OPTIONS
==========================================================================

First keep the product useful locally. Avoid requiring hosted queues, remote
media storage, paid APIs, or accounts for the first reliable download workflow.

Costs to plan explicitly:
  Developer time; Windows/macOS test access; release signing; security review;
  distribution bandwidth; platform compatibility maintenance; support; and,
  if introduced, AI inference, hosting, storage, and abuse handling.

Useful cost formulas:
  Hosted transfer cost depends on downloaded GB, processing copies, outgoing
  GB, storage GB-days, and worker time. Long videos and concurrency multiply it.
  AI cost depends on processed audio/video duration or tokens, model choice,
  device/cloud hardware, and retained indexes. "Free API" is not a durable plan.

Possible business approaches for later owner choice:
  - An open-source project with support/sponsorship.
  - A free reliable core with optional paid productivity features.
  - A desktop license with an explicitly defined update/support policy.
  - Optional paid cloud/AI processing with visible quotas and local alternatives.
  - Team/self-hosted support if real demand emerges.

Do not choose pricing before validating user value, license compatibility,
support capacity, and operating costs. Do not monetize bypass capabilities or
make basic file recovery depend on an unrelated AI subscription.

20. RISKS AND HOW WE REDUCE WASTED WORK
==========================================================================

Risk: five projects become five disconnected products.
  Response: select one engine, one job model, and one browser bridge. Adapt
  missing capabilities selectively rather than merging unrelated runtimes.

Risk: the foundation cannot build or its maintenance cost is unacceptable.
  Response: reproduce it early; inventory exact toolchains; compare alternatives
  with evidence before choosing a rewrite. Do not disable trust verification.

Risk: historic audit findings are treated as current truth forever.
  Response: preserve them as dated evidence and recheck the actual selected
  snapshots. A previous network failure may be resolved; a successful bundle
  build may still hide type, runtime, permission, or dependency problems.

Risk: adding platforms creates permanent compatibility debt.
  Response: limit the supported catalogue, name maintainers, test approved
  workflows, and show degraded status when maintenance is not available.

Risk: cloud media processing becomes expensive or exposes private data.
  Response: local-first design, opt-in upload, bounded quotas, cleanup, and
  cost measurements before any public hosted service.

Risk: language migration consumes the budget before a product exists.
  Response: reuse the chosen foundation until an evidence-based comparison
  shows a worthwhile migration benefit.

Risk: AI features distract from basic correctness.
  Response: ship reliable transfers and safe processing first. Add AI with
  evaluation datasets and ordinary controls/fallbacks.

Risk: workspace or AI conversation loss loses progress.
  Response: commit and push meaningful completed work directly to main at
  least every five minutes during active changes, as the owner requested.
  Keep concise evidence and next steps in versioned documents. Local commits
  alone do not protect against losing the machine; report blocked pushes.

24. THE PRODUCT WE SHOULD AIM TO EARN
==========================================================================

One coherent, dependable product that reuses the substantial work already
available; supports a growing, tested set of permitted video/file workflows;
and makes local media management easier through useful, optional AI.

The first achievement should be a download users can trust to finish correctly.
The one-year ambition is a credible supported product, not an unchecked list
of websites. The two-year ambition is sustainable breadth and smarter personal
media tools. Beyond that, expand only where users, evidence, maintainers, and
resources justify the work.

that every source, format, restriction, or missing original can be solved.

enough to prove and preserve.
